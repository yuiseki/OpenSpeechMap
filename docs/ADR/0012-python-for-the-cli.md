# ADR 0012: CLI は Python で書き、外部プログラムの薄いラッパーに留める

- 状態: Accepted (2026-08-23)
- 文脈タグ: 設計, 言語

## 背景
最初の実装は bash だった。`aiq extract` / `locitorium resolve` / `detempus` を呼ぶだけなので、
シェルで足りると考えた。実際に動いたが、製品 として他人に触らせるには次が効いてきた。

- 引数解析を手書きしている。148 行のうち 40 行が `while`/`case` で、`-` を標準入力として
  扱う分岐を書き忘れていた(`-*` のパターンに先に当たっていた)
- テストの期待値が locale 依存の `sort` で揺れた
- ロジックが shell と jq に分散し、どちらを読めばよいか分からない
- 型がない。detempus と locitorium の出力の形が `web/src/types.ts` にしか書かれていない
- **実行中のスクリプトを編集すると壊れる。** bash はスクリプトを逐次読むので、走っている
  最中に編集するとバイト位置がずれる。実際に長時間実行の途中で編集し、`geojson` の途中から
  再開して `son` をコマンドとして実行し落ちた

HOTOSM は [0004](https://docs.hotosm.org/decisions/0004-python/) でバックエンド言語を Python に
決めている。理由として挙げているのは、コミュニティが貢献しやすいこと、開発が速いこと、
ライブラリが豊富なこと、Python の経験者が多く委託先の選択肢が広がること。この製品の
聴衆は HOTOSM と重なるので、同じ言語であること自体に価値がある。

## 決定
CLI を Python で書く。ただし **bash と同じく薄いラッパーに留める**。分析も地名解決も
時系列も、外部プログラムを呼ぶ。

境界の引き方はこうする。

| やること | どこで |
|---|---|
| レンズの適用 | `aiq extract` を subprocess で |
| 地名の接地 | `locitorium resolve` を subprocess で |
| 時系列の分析 | `detempus` を subprocess で |
| 利用者が書いた絞り込み式 | `jq` を subprocess で |
| ゲートの語彙照合 | Python で。3 行の部分文字列判定に grep を起動する理由がない |
| 地点への時刻の join | Python で。辞書の参照 |
| 引数解析・検証・エラーメッセージ | Python で |

`detempus` は `analyze` を、`locitorium` は `resolve_records` を import できることを確認した
うえで、あえて subprocess にしている。ライブラリとして取り込むと、その版に釘付けになり、
呼び出し側が手元の作業ツリーを差し替えて試すことができなくなる。CLI 越しなら
`DETEMPUS=~/checkout` で切り替えられる。

## 影響
`typer` だけが依存になった。他は import しないので依存に書かない。代わりに
`speechmap --check` が、どのプログラムがどこで見つかったかを報告する。長い処理の途中で
気づくより、走らせる前に聞けたほうがよい。

テストが 60 件になった。bash 版から移す過程で、期待値の誤りが 3 件、実装の誤りが 1 件
見つかった。

`env --chdir` で checkout の版を呼ぶときは `VIRTUAL_ENV` を外す必要があった。これを
外さないと、呼び出し側の virtualenv を uv が優先し、コンポーネントを別の場所に探しに行く。

## 検討した代替案
- **bash のまま**: 却下。上記の具体的な不都合と、HOTOSM 0004 との不一致
- **エンドポイントを直接叩き、aiq を経由しない**: 却下。Python から Python の CLI を
  subprocess で呼んで HTTP を投げるのは一段無駄だという議論は成立するが、薄いラッパーに
  留めるという方針を選んだ。`aiq extract` にある同時実行と 1 件入れて 1 件出す保証を
  書き直さずに済む
- **detempus / locitorium をライブラリとして import**: 却下。上記のとおり、版の切り替えが
  効かなくなる
