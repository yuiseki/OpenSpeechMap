# ADR 0001: エージェントが駆動する前提で設計し、GUI を作らない

- 状態: Accepted (2026-08-23)
- 文脈タグ: 設計, インターフェース

## 背景
この種のパイプラインの手本は WebODM だった。ブラウザに写真のフォルダをドラッグすると
オルソモザイクが出てくる、という体験が OpenDroneMap を広めた。同じものを作るべきかを
検討した。

しかし動かし方が変わっている。実際に OpenDroneMap でオルソ画像を作っている利用者が
WebODM を一度も使わず、すべて AI エージェントに依頼している。ブラウザでファイルを
D&D してプログレスバーを眺めたい人はもういない。

## 決定
GUI を作らない。エージェントが駆動できる interface に投資する。具体的には次を守る。

- 各段が標準入力を読み標準出力に JSONL を書く。段を繋げられる
- 1 件入れて必ず 1 件出す。処理できないレコードも null を埋めて通す。件数が減ると
  呼び出し側が結果を入力に突き合わせられなくなり、しかもそれが黙って起きる
- 想定される失敗は traceback ではなく一行の説明。読めない時刻や未導入の依存は
  呼ぶ側が自分で直せる種類の失敗で、Python の内部構造は関係ない
- 対話プロンプトを持たない。再実行が安全
- `AGENTS.md` を置き、エージェントがそれを読めば人に聞かずに動かせるようにする

## 影響
UNIX 哲学に寄せた設計が、そのままエージェント向けの受け口になった。両者は別の要求では
なく同じ要求だった。locitorium の CLI 化、detempus の契約、aiq の標準出力の修正は
どれも「パイプで繋げるように」という動機で行ったが、結果としてエージェントが扱える
ものになっている。

各段がファイルを書くので、後の段だけを作り直せる。中間出力を目で確かめられる。

## 検討した代替案
- **Web UI を作る**: 却下。投資先が変わった。必要になれば後から足せるが、逆は難しい
- **対話的な CLI**: 却下。エージェントが詰まる
