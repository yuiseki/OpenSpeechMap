# ADR 0007: 各レコードに provenance を持たせる

- 状態: Accepted (2026-08-23、前身 PoC で 2026-08-20 に導入)
- 文脈タグ: 再現性, 運用

## 背景
同じ入力を再処理したときに判定が変わることがある。原因の候補は複数ある。プロンプトを
変えた、モデルを変えた、安いふるいで弾かれた、ふるいの閾値を変えた、モデルの推論が
非決定的だった。レコードに何も残っていないと、どれが原因か後から切り分けられない。

前身の PoC では実際に、プロンプトを 2026-08-16 に変更した前後で過去日と条件が揃わなく
なり、急増検知が `topic` ではなく生テキストを見る設計を選ぶ理由になった。

## 決定
各レコードに、どの仕組みのどのプロンプト版で判定したかを残す。

- 仕組み: `llm` / `heuristic` / `screened` / `embedding` のいずれか
- プロンプト版: system と instruction を連結した sha256 の先頭 10 桁
- スコアと閾値があれば、その値も

分類器のプロンプト指紋が現在のプロンプトと一致しない場合、ふるいを無効化して全件を
LLM に回す。古い分類器で新しいプロンプトの結果を絞ってはいけない。

## 影響
プロンプトを変えると指紋が変わるので、混在したデータでも由来を追える。

これは実務上の制約も生む。プロンプトの推敲は指紋を変えるので、既存の記録と繋がらなく
なる。レンズの `instruction.txt` に出力スキーマが散文で重複しているのは、
`response_format` で不要になった今も消していない。消すと指紋が変わる。

## 検討した代替案
- **プロンプトの全文を各レコードに埋める**: 却下。1 レコードあたり数百バイト増え、
  同じ文字列が何万回も繰り返される
- **バージョン番号を手で振る**: 却下。上げ忘れる。内容から導出される値でなければ
  信頼できない
