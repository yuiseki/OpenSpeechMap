# ADR 0003: 既存 OSS を束ね、隙間だけを作る

- 状態: Accepted (2026-08-23)
- 文脈タグ: 設計, OSS

## 背景
OpenDroneMap はすべてを自分で作っていない。OpenSfM を fork している。HOTOSM はもっと
顕著で、DroneTM は QGroundControl も MAVLink も ArduPilot も作り直さず、既存 OSS が
埋めていない隙間、つまり AOI から飛行計画を作る部分と撮影後の QA・カバレッジ検査だけを
担っている。

同じ目で前身の PoC を見ると、自作が厚いのは 5 箇所だけで、そのうち隙間を埋めていると
言えるのは 2 つだった。残りは薄い層か、束ねる側の仕事だった。

## 決定
既存 OSS に任せる。ffmpeg、whisper.cpp、llama.cpp、Nominatim、MapLibre、PMTiles、
statsmodels、ruptures。

単体で価値があり他の探求にも使えるものだけを部品として外に出す。

| 部品 | 役割 | 性格 |
|---|---|---|
| locitorium | テキスト → OSM 実体に接地された地点 | 真の隙間。他に無い |
| detempus | 時刻付きの数え上げ → 異常候補と変化点 | 真の隙間。探して無かった |
| aiq (fork) | テキスト → ラベル / 構造化 / 埋め込み | 既存を改修 |

このリポジトリは束ねる側だけを持つ。

## 影響
fork した aiq に足したのは 2 点だけだった。`extract`(JSON Schema で複数フィールドを
1 回の呼び出しで取得)と `classify --score-field`(スコアを出力しカスケードの閾値判定を
`jq` に委ねる)。作り直せば数千行になっていたものが、496 行のコードに 2 機能を足す
作業になった。

## 検討した代替案
- **aiq を作り直す**: 一度そう考えたが撤回した。行数を見る前に判断していた。実際は
  496 行で設計思想も正しく、直すべきは 4 点だった。**行数を見てから決める**
- **すべてを 1 つのリポジトリに入れる**: 却下。部品が他の探求に使えなくなる。
  時系列の異常検知は放送と無関係に価値がある
- **既にあるものを探さずに作る**: 時系列の異常検知については探してから作った。
  Python ライブラリは呼び出しコードを毎回書くことになり、クラウド CLI は自社サービスの
  操作用で、監視基盤付属の CLI はデータが基盤の中にある前提だった。この確認をした上で
  作ったので、埋め込みサーバーの構築で公式イメージを見ずにホストのバイナリを持ち込もう
  として依存を 3 段追いかけた失敗とは対照的だった
