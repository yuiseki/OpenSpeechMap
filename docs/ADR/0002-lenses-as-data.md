# ADR 0002: レンズをコードではなくデータにする

- 状態: Accepted (2026-08-23)
- 文脈タグ: 設計, LLM, 再利用

## 背景
前身の PoC には 3 つの分類器があった。災害(`classify_grid.py`)、人道安全保障
(`classify_humansec.py`)、催事(`classify_festival.py`)。3 つを並べて比べると骨格が
ほぼ同じで、違うのは system プロンプト、instruction、ゲートのキーワード、出力
フィールド名だけだった。**3 ファイルの差分はコードである必要がなかった。**

## 決定
レンズを 3 つのテキストファイルにする。

| ファイル | 必須 | 役割 |
|---|---|---|
| `schema.json` | はい | 抽出するフィールドの JSON Schema |
| `instruction.txt` | はい | 各レコードに対して何をするか。本文はこの後ろに付く |
| `system.txt` | いいえ | システムプロンプト |
| `gate.txt` | いいえ | 1 行 1 キーワード。どれかを含むレコードだけが LLM に届く |

ゲートを 4 つ目のファイルにしたのは、当初 3 ファイルで設計したところ、催事レンズを
移してきて穴が見つかったためである。前身の PoC ではゲートの語彙が Python の中に
あった。それを外に出さないと、催事レンズをこの形で再現できない。ゲートは `grep -F -f`
で足りるので、道具を増やす必要はなかった。

スキーマは `response_format: json_schema` としてエンドポイントに渡す。出力の形を
プロンプトで丁寧に頼むのではなく、デコーダの制約にする。対応していない
エンドポイント向けの逃げ道は用意するが、黙って切り替えることはしない。

## 影響
テーマを変えるのに Python を 1 行も書かない。災害から人道安全保障や催事へ、レンズ
ディレクトリを差し替えるだけで移る。

8/13 19時台の 30 セグメントで、この形が元の Python 実装を再現するか比較した。
`is_disaster` が 30/30 一致。`category` は 3 件相違だが、いずれも野球結果と大雨実況が
同一セグメントに混ざった境界事例で、旧新どちらの割り当ても妥当だった。

比較の際、最初は instruction を短く書き直して測り 3 件の不一致を出した。原因は仕組み
ではなく書き直したプロンプトだった。**比較には元の instruction と system をそのまま
使う必要がある。**

## 検討した代替案
- **レンズごとに Python を書く**: 現状の PoC。差分がプロンプトとゲートの語彙だけなので不要
- **ゲートを引数で渡す**: 却下。ゲートの語彙はレンズの一部であり、レンズを配布したら
  一緒に付いてくるべきもの。呼び出し側が毎回思い出すものではない
- **1 ファイルにまとめた独自形式**: 却下。3 つは直交しており、既存の JSON Schema と
  プレーンテキストで足りる。新しい形式を発明する理由がない
