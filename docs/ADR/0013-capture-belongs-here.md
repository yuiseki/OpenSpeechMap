# ADR 0013: 常時録音をこのリポジトリに置く

- 状態: Accepted (2026-08-23)
- 文脈タグ: 設計, 入力

## 背景
ADR 0004 で入力面を「時刻付きテキスト」と定義した。録音はそれより更に上流で、
この repo の範囲を広げることになる。

一方 ADR 0003 は「既存 OSS を束ね、隙間だけを作る」と決めている。録音そのものは
ffmpeg がやる。では録音の監視役は隙間なのか。

## 決定
置く。`speechmap-record` として。

隙間である理由が 2 つある。

**ffmpeg は落ちたら落ちたままである。** USB の一瞬の不調で rtl_fm が死ぬと、ffmpeg も
一緒に終わる。そして誰も気づかない。3 週間前に止まった録音は、動いている録音と
見た目が同じである。実際に前身の PoC でワンセグの録音が 23 日間空回りしていた。
ffmpeg のプロセスは生きていて、出力は 7 月 31 日で止まっていた。

**ffmpeg はディスクを空けない。** 常時録音は放っておけばディスクを埋める。経過時間と
合計サイズの両方で古いものから消す必要があり、しかも書き込み中の最新ファイルには
触れてはいけない。

そして範囲の話については、**ファイル名に埋まる時刻が下流が時刻を得る唯一の経路である**。
`<LABEL>-YYYYMMDD-HHMMSS.ts` という命名がそれを運ぶ。音声メタデータを読む段は
このパイプラインに存在しない。放送を扱う場合、捕獲しなければ分析する対象が無い。

## 影響
`--source sdr` と `--source http` の 2 つ。前者は RTL-SDR の USB チューナーから実電波を、
後者は SHOUTcast / Icecast / HLS などの任意のストリームを受ける。

HTTP 側は再エンコードせず copy する。SHOUTcast の多くは MP3 で、復号して再符号化する
利益が無い。mpegts の中の MP3 は下流で問題なく読める。

`-reconnect` 系は省略できない。配信ホストは長時間の接続を切る。付けないと一晩の録音が
10 分になる。実際にそうなった。

SDR 側はシェル経由のパイプで、`set -o pipefail` が必須である。これが無いと rtl_fm が
死んでも ffmpeg が閉じたパイプに座り続け、監視役が異常を知れない。

テストはリテンションの判定と ffmpeg に渡すコマンドの組み立てを検証する。無線機も
ネットワークも要らない。監視役の再起動はプロセスの偽物で確かめる。

## 検討した代替案
- **録音は利用者に任せる**: 却下。上記 2 つの落とし穴を各自が踏み直すことになる。
  どちらも黙って起きる種類の失敗である
- **systemd や supervisor に任せる**: 再起動はそれで足りるが、リテンションは足りない。
  そして「最新のファイルには触らない」という条件は録音の形式を知らないと書けない
- **別のリポジトリにする**: 却下。ファイル名の命名規約がこのパイプラインとの契約なので、
  離すと二か所で守ることになる
